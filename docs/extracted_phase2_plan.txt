1. Executive Summary
Objective: Turn CyberSentinel DWM into a visible, real, queryable cybersecurity Data Warehouse instead of treating DWM as only a risk-scoring formula.
Warehouse platform: Google BigQuery. It is the managed analytical store; users do not manage a database server.
Source data: Existing network.json / cves.json plus NVD/CISA enrichment generated by the current repo scripts.
Analytical model: One primary Star Schema centered on fact_cyber_risk. The fact is at node/event grain; attack-path fields are recorded per hop so a complete path can be reconstructed with SQL.
Live ingestion: Every simulation writes Top-K path observations into BigQuery; every remediation event can be recorded as a new observation so history is preserved.
User access: CyberSentinel UI analytics, a read-only SQL console, Google Cloud bq CLI / Cloud Shell, and Google Colab.
Data mining: Historical attack-path frequency, recurring pivots, vulnerable software/CVE patterns, risk trends, and optional ML-training datasets.
DWM feedback: Keep current DWM math intact; use the warehouse to compute historical features and comparative analytics that explain or later enrich DWM/ML scoring.
Important correction from the earlier discussion:   If BigQuery is the warehouse, terminal access is via the Google Cloud bq CLI (or Cloud Shell), not psql. BigQuery uses GoogleSQL in the console/API and supports the bq command-line tool.

Decision 1 — BigQuery: The warehouse is created as a BigQuery dataset inside a Google Cloud project.
Decision 2 — One visible Star: Use one central fact_cyber_risk plus dimension tables so the project can clearly present a Star Schema. Supporting topology/derived tables are outside the primary star.
Decision 3 — No direct browser credentials: React talks to FastAPI; FastAPI queries BigQuery. The browser never receives a service-account key.
Decision 4 — Keep operational simulation separate from analytics: Graph/pathfinding stays in memory and returns results fast. Warehouse writes happen asynchronously/background so they cannot block the simulation path.
Decision 5 — Append history: Do not overwrite risk history. New risk observations/remediation states become new fact rows so trends and comparisons remain possible.
Decision 6 — Views for UI: The UI reads curated BigQuery views instead of issuing arbitrary complex joins for every dashboard widget.
Decision 7 — Query console is read-only: UI SQL accepts SELECT/WITH only; block mutation/DDL statements and set a BigQuery maximum bytes billed for safety/cost control.
BigQuery terminology: A dataset is the container for tables/views; a table stores rows/columns; GoogleSQL is the query language; the bq CLI can create/query tables from a terminal. The official docs describe BigQuery as a fully managed analytics data warehouse and document bq/GoogleSQL usage.
4. Final Data Warehouse Star Schema
Grain of the central fact:   One row = one security observation for one network node/CVE at one timestamp. For an attack simulation, each hop of each ranked path is one observation row. Path-level values such as path_rank, total_hops, and total_weight are repeated across the rows of that path; curated views hide the duplication for analysts.

6.1 Initial load vs incremental load
Initial bootstrap: load all three networks, their nodes, all CVEs, all available DWM fields, and a baseline risk observation for each node/CVE pair.
Incremental source refresh: when JSON changes, load only changed/added CVE or node records. Prefer staging tables + MERGE for dimensions.
Simulation ingestion: append-only facts; do not update the entire fact table after every simulation.
Remediation ingestion: append a new observation row rather than overwriting history.

9.3 Query console behavior
1. User enters SELECT/WITH query against authorized dataset views/tables.
2. Frontend sends query text to POST /warehouse/query.
3. FastAPI validates read-only syntax and optionally injects a dataset prefix / allowlisted table policy.
4. Backend sends the query to BigQuery with a maximum bytes billed and timeout.
5. Backend returns column metadata + rows + job statistics for UI display.
6. UI renders a table and shows elapsed time / rows returned; query text can be copied for Colab or bq CLI.

12. Security, Access, Cost, and Reliability
Credentials: Use Google Cloud Application Default Credentials locally or a workload/service identity in deployment. Do not commit service-account JSON to GitHub.
Frontend access: Never expose BigQuery credentials to React. React calls FastAPI only.
IAM: Backend service identity needs only the minimum BigQuery job/data permissions required. Analysts can have read access; ETL identity needs write access.
SQL console: Allow SELECT/WITH; reject INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/TRUNCATE/EXPORT/LOAD in the UI query endpoint.
Cost guard: Set maximum bytes billed and a sensible query timeout for UI-generated jobs.
Partitioning: Partition fact_cyber_risk by event date to reduce scans of historical data.
Clustering: Cluster fact_cyber_risk by network/node/CVE or another validated access pattern once query volume is known.
Failure behavior: Warehouse failure must not break simulation. If BigQuery logging fails, the simulation continues and the backend reports an internal log warning.
Auditability: Record source/data_source and schema_version in simulation metadata so changes can be traced.
PII: Do not put real customer data in the hackathon warehouse. Store simulated bank infrastructure and security telemetry only.

Appendix B. Sample Analytics Queries
1. Critical KEV vulnerabilities on public-facing nodes
SELECT
  n.name AS node,
  c.cve_id,
  f.base_cvss,
  f.contextual_risk_score,
  f.kev_listed
FROM `PROJECT_ID.cybersentinel_dw.fact_cyber_risk` f
JOIN `PROJECT_ID.cybersentinel_dw.dim_node` n USING(node_key)
JOIN `PROJECT_ID.cybersentinel_dw.dim_cve` c USING(cve_key)
WHERE f.observation_type = 'BASELINE_VULNERABILITY'
  AND n.exposure = 'public'
  AND f.kev_listed = TRUE
  AND f.base_cvss >= 9
ORDER BY f.contextual_risk_score DESC;
2. Most common pivot nodes in top-3 paths
SELECT
  n.name,
  COUNT(DISTINCT CONCAT(f.simulation_id, '-', f.path_id)) AS path_count
FROM `PROJECT_ID.cybersentinel_dw.fact_cyber_risk` f
JOIN `PROJECT_ID.cybersentinel_dw.dim_node` n USING(node_key)
WHERE f.observation_type = 'ATTACK_PATH'
  AND f.path_rank <= 3
  AND f.hop_number > 1
GROUP BY n.name
ORDER BY path_count DESC
LIMIT 10;
3. Reconstruct the most frequent attack sequences
SELECT
  path_rank,
  COUNT(*) AS occurrences,
  STRING_AGG(n.node_id, ' -> ' ORDER BY f.hop_number) AS route
FROM `PROJECT_ID.cybersentinel_dw.fact_cyber_risk` f
JOIN `PROJECT_ID.cybersentinel_dw.dim_node` n USING(node_key)
WHERE f.observation_type = 'ATTACK_PATH'
GROUP BY simulation_id, path_id, path_rank
ORDER BY occurrences DESC, path_rank
LIMIT 20;
4. Static vs DWM path comparison
SELECT
  simulation_id,
  weighting_mode,
  path_rank,
  total_hops,
  total_weight
FROM `PROJECT_ID.cybersentinel_dw.vw_attack_path_history`
WHERE network_id = 'enterprise-bank'
  AND target_node_id = 'swift_terminal'
ORDER BY simulation_id, weighting_mode, path_rank;
5. Risk trend by network
SELECT
  DATE(event_timestamp) AS day,
  network_id,
  AVG(contextual_risk_score) AS avg_risk,
  MAX(contextual_risk_score) AS max_risk
FROM `PROJECT_ID.cybersentinel_dw.fact_cyber_risk`
WHERE contextual_risk_score IS NOT NULL
GROUP BY day, network_id
ORDER BY day, network_id;
6. Open remediation queue
SELECT
  n.name AS node,
  c.cve_id,
  f.base_cvss,
  f.contextual_risk_score,
  f.remediation_priority
FROM `PROJECT_ID.cybersentinel_dw.fact_cyber_risk` f
JOIN `PROJECT_ID.cybersentinel_dw.dim_node` n USING(node_key)
JOIN `PROJECT_ID.cybersentinel_dw.dim_cve` c USING(cve_key)
WHERE f.remediation_status IN ('OPEN', 'RECOMMENDED')
ORDER BY f.contextual_risk_score DESC;
